# Design

## Context

[Proposal](proposal.md), [контекст](../../../docs/ai/PROJECT-CONTEXT.md).
Кода продукта нет. Разрешена документация, основа утверждена; реализация не разрешена.
Уточнения человека Q-01/Q-04/Q-05 и семантика Q-07/Q-08 отражены в specs.
DD-01–DD-05 ниже — design decisions оркестратора в разрешённом объёме,
не бизнес-требования человека. Ранее изложенные Q-02/Q-09/Q-10 сохранены как
контекст предыдущего сообщения, а не приписаны последнему списку бизнес-решений.
Postmark и бюджет £75–150/месяц — заданные эксплуатационные ограничения.

## Goals / Non-Goals

**Goals:** транзакционные операции, безопасные платежи/аккаунты, готовая CMS,
проверяемый рост до 5–10 тысяч SKU.
**Non-Goals:** микросервисы, брокер, Redis/поисковый кластер без измеренной нужды,
POS/ERP, перевозчик API и функции после MVP.

## Decisions

### Утверждённая основа

TypeScript/Next.js/Payload/PostgreSQL, pg_trgm, Stripe Checkout, объектное хранилище,
обработчик задач на БД. Отдельные CMS/backend добавили бы развёртывания и синхронизацию.
Payload не заменяет доменные правила магазина.
[Payload](https://payloadcms.com/docs/getting-started/installation),
[pg_trgm](https://www.postgresql.org/docs/current/pgtrgm.html).

### Предложение данных и операций

[Схема модулей](../../../docs/architecture.md). Продаваемый физический остаток отделён
от резервов; выделение всей корзины одной транзакцией и блокировками в стабильном порядке.
Административные продажи используют тот же контроль. Корректировки, затрагивающие
резервы, требуют явного разрешения конфликта; нельзя молча нарушать обеспечение заказов.
Не вычитать резерв/продажу дважды. Денежный возврат не увеличивает остаток;
товар возвращается в продаваемый остаток только после проверки.

### Stripe и срок

Сервер фиксирует начало оплаты и deadline UTC + 30 минут; retry его не продлевает.
Резерв и внешняя session не являются одной транзакцией: устойчивый intent,
idempotency key, компенсация при сбое API, сверка неопределённых результатов.
Stripe expires_at минимум через 30 минут после создания session; задержка API
не позволяет гарантировать совпадение с исходным deadline до миллисекунды.
Правило резерва задаёт бэкенд; session закрывается при истечении; поздний успех
обрабатывается утверждённой перепроверкой всей корзины. Retry новой session
не продлевает резерв, даже если технический срок session длиннее.
[Сроки Stripe](https://docs.stripe.com/payments/checkout/managing-limited-inventory.md?payment-ui=stripe-hosted).

Webhook: подпись, GBP/сумма/заказ, уникальность event и факта платежа, обработка
повторов и событий не по порядку. Redirect не подтверждает оплату.
Поздний успех после обычного истечения: атомарно выделить всю корзину либо немедленно
инициировать полный возврат и уведомить; не исполнять частично. Принятая сервером
явная отмена имеет приоритет: cancelled не восстанавливается даже при наличии.
Отмена и webhook сериализуют переход заказа блокировкой той же записи. Не сравнивать
часы браузера с доставкой событий Stripe. Если платёж обработан первым, отмена идёт
через предусмотренный запрос, исполнение блокируется до его разрешения.
Две успешные попытки одного заказа не порождают два заказа: денежный излишек
обнаруживается и корректируется. Повтор внешнего запроса с idempotency key.
[Webhooks](https://docs.stripe.com/webhooks), [refunds](https://docs.stripe.com/refunds).

Успешная оплата переводит временный резерв в выделение оплаченного заказа в одной
транзакции с confirmed. 30-минутное истечение больше не освобождает оплаченные позиции.
Возврат не restock. Обязательство полного refund позднего платежа и outbox фиксируются
в одной транзакции; один ключ на обязательство, сверка неопределённых ответов перед retry.
failed не оставлять в бесконечном retry: сотрудник организует допустимый альтернативный
возврат, согласованный с покупателем, если исходный способ окончательно недоступен.

### DD-01 — VAT, округление и возвраты (Q-03)

**Источник:** делегированное техническое решение, CHK-04; UK VAT-registered,
gross B2C/GBP уже входят в baseline. Это минимальный воспроизводимый алгоритм,
а не заявление о применении магазином специальной VAT retail scheme.

SKU ссылается на Tax Category из расширяемого справочника: STANDARD и ZERO_RATE.
Ставка хранится отдельно с периодом действия; стартовые ставки 20% и 0%. Новый класс
не меняет структуру SKU. Нулевая ставка не означает exempt. До публикации конкретные
SKU классифицируются по фактическим товарам и правилам HMRC, без ставки по догадке.
Неизвестная категория/ставка блокирует продажу, а не заменяется 20%.

Деньги хранятся целыми пенсами; промежуточная арифметика — точные целые/рациональные
значения, без binary float. Ставка r в basis points (20% = 2000):

1. Для строки с количеством q и оплачиваемой gross-ценой g за единицу: G = q × g.
   При оформлении используется действующая сниженная цена, обычная — справочная.
2. VAT строки V = roundHalfUp(G × r / (10000 + r)); N = G − V.
   Округление один раз на строку до пенни, ровно половина — вверх.
   Отрицательные корректировки получают знак после расчёта положительного возврата.
3. Итоги — суммы строк, не повторное вычисление VAT от общего gross. Всегда N + V = G.
4. Доставка включена в договор продажи. Её gross D распределяется по строкам
   пропорционально G: floor(D × G / ΣG), остаточные пенсы — по убыванию дробного
   остатка, при равенстве — по сохранённому номеру строки. VAT доли доставки считается
   по категории строки тем же roundHalfUp. Нулевая доставка даёт нули; ΣG = 0
   при ненулевой D блокирует расчёт для ручного решения. Отдельная самостоятельная
   услуга доставки в MVP не предлагается, её VAT treatment потребовал бы другого правила.
5. VAT Snapshot хранит категории, ставки/даты, tax point и основание, q/g/G/N/V,
   доли доставки, версию алгоритма и тарифа. При оформлении сохраняется quote;
   законный tax point определяется по факту оплаты/поставки/VAT invoice, не по одному
   confirmed. При необходимой корректировке создаётся новый снимок с основанием,
   gross покупателю не повышается, исходный снимок не перезаписывается.
   Order received/confirmed не объявляются VAT invoice автоматически.
6. Для возврата k из q единиц cumulative VAT = roundHalfUp(V × k / q).
   VAT очередного возврата — разность cumulative после и до; gross = g × количество,
   net = gross − VAT. Уже одобренные pending-возвраты также учитываются под блокировкой.
   Все q единиц возвращают ровно G и V. Доставка возвращается по RET-05 с VAT
   из исходного распределения и тем же принципом остатка. Новые ставки не применяются.
   Возврат/credit note добавляет корректировку со ссылкой на исходный снимок.

Пример: STANDARD £120 (net £100, VAT £20), ZERO_RATE £60, доставка £12.
Доли доставки £8 и £4; VAT доставки £1.33 и £0; заказ gross £192, VAT £21.33,
net £170.67. Три единицы по £0.01 при 20% дают VAT строки £0.01:
возврат по единице даёт VAT £0, £0.01, £0; полный возврат точно сходится.

Альтернативы: VAT по единице или только по заказу создают другую разбивку количества;
в MVP не смешивать методы. Stripe Tax не нужен для этих категорий/территории;
Stripe получает серверный gross и не добавляет второй налог. Обоснование:
[HMRC §17.6](https://www.gov.uk/guidance/vat-guide-notice-700),
[VAT доставки](https://www.gov.uk/guidance/vat-on-postage-delivery-and-direct-marketing-notice-70024).
Пропорциональное распределение — выбранный design decision, не дословное требование HMRC.
Ассортимент, tax point и договор проверяются бухгалтером перед выпуском.

### Самовывоз и состояния

Семантика — INV-05 и FUL-02. Хранить UTC, считать календарь Europe/London с DST.
Дни/закрытие/праздники задаются календарём выбранного магазина, не угадываются Mon–Fri.
Deadline подготовки — закрытие следующего рабочего дня после локальной даты confirmed.
Пропуск уведомляет менеджера/клиента, но не отменяет заказ и не начинает pickup countdown.
ready фиксируется один раз; конец срока — исключительная граница 00:00 даты ready + 4 дня.
Понедельник ready → четверг включительно; максимум продления → воскресенье включительно.
Продление атомарно до исходного срока; автор/причина/время сохраняются. Истечение и
выдача блокируют тот же заказ; истёкший неоплаченный самовывоз отменяется с однократным
освобождением резерва и уведомлением. Задержка подготовки не создаёт штраф/автоотмену.

Внутреннее представление — техническая декомпозиция семантики Q-08:

| Группа | Состояния и переходы |
|---|---|
| Order State | created → confirmed → completed; created/confirmed → cancel-requested → cancelled либо немедленно cancelled для неоплаченного отказа; completed сохраняется после возврата |
| Payment State | unpaid → pending → paid; неудача сохраняет попытку и unpaid; refund-pending/refund-failed показываются вместе с уже возвращённой суммой; partially-refunded/refunded после денежного подтверждения |
| Fulfilment State — доставка | unprepared → dispatched → delivered |
| Fulfilment State — самовывоз | unprepared → ready-for-pickup → collected |

awaiting payment — отображение created + pending/unpaid доставки, не смешанный статус.
Истёкший онлайн-резерв хранит expired в Reservation; Order остаётся created без
активного резерва, что допускает PAY-03, но не обычный retry после deadline.
У cancelled дальнейшее исполнение запрещено; произошедшие факты не стираются.
Отмена после dispatched возможна по принятому законному обращению до completed
с возвратом/перехватом отправления; запрос не имитирует физический возврат.
Гонка получения/отмены решается атомарно: после delivered/collected обрабатывается
возврат completed-заказа. Сам запрос отмены не имитирует остановку посылки в пути.
Возврат денег не переводит Order State в cancelled автоматически.

Если после отмены посылка фактически всё же получена, сохранить факт доставки
и обработать возврат, но не восстановить cancelled и не сделать его completed.
Менеджер вручную регистрирует dispatched и подтверждение ТК для delivered с
основанием/временем/автором; API перевозчика вне MVP. collected требует полной оплаты
в магазине и явной выдачи. Для действующего заказа delivered/collected и completed — одна транзакция.
Order received и confirmed — разные события писем; у самовывоза возможны сразу,
у доставки раздельно по факту оплаты. Готовность не равна получению.

### DD-02 — каталог и доставка: минимальные defaults

Для общего каталога выбрать разрешённую Q-07 альтернативу: From по минимальной
текущей цене подходящих SKU без привязки к наличию, наличие «в сети» отдельно.
При In stock учитывать доступность в сети и цену только подходящих доступных SKU.
Доставка использует склад, самовывоз — выбранный магазин. Если In stock выключен
и доступных вариантов нет, минимум подходящих SKU с явным отсутствием наличия,
без обещания покупки. count — distinct моделей, все условия — на одном SKU;
одна выборка для карточек/count/цены/сортировки. Recommended в каталоге — ручной
порядок CMS и устойчивый ID, relevance поиска — pg_trgm с точным артикулом первым.

Shipping Class: STANDARD_PARCEL, BICYCLE, OVERSIZED_NON_BICYCLE. Shipping Tariff
версионирует зоны, gross-базу класса, включённое количество и доплату за единицу
сверх включённого по каждому классу. Расчёт: max баз присутствующих классов + сумма
их настроенных доплат. Нулевая доплата задаётся явно. При равенстве баз выбирается
устойчивый код; сумма не меняется. Oversized не-велосипед не попадает в BICYCLE.
Не вычислять упаковку. Адреса/postcode — проверенная версионированная таблица
с точными исключениями, не запрет префикса, содержащего одновременно материк/острова.
Непроверенный адрес или отсутствующий тариф блокирует доставку. Зоны, суммы,
доплаты и календари — launch data сотрудников по реальным расходам/часам;
это не основание выдумать цену или новый нерешённый алгоритм при разработке.

### Возвраты: сроки и обязанности (Q-05)

Product Return хранит Return Reason: CHANGE_OF_MIND, FAULTY, WRONG_ITEM. Последние
два используют общий workflow за счёт бизнеса, сохраняя разные причины.
Обычный возврат оплачивает покупатель только после надлежащего преддоговорного
информирования, включая требуемую информацию о расходах непочтовых товаров.
Исходная доставка возвращается по RET-05; ошибка/брак не ограничиваются правилами
возврата по желанию. Факт денежного возврата отделён от решения restock.

«Немедленно»: при установлении права/суммы либо автоматическом PAY-03 сохранить
обязанность и outbox одной транзакцией, первая попытка в доступном worker без пакетного
ожидания (техническая цель ≤ 60 секунд, задержка > 5 минут — alert). Outage не теряет
обязанность. В предусмотренных обстоятельствах CCR допускает удержание до получения
товара либо доказательства отправки; внутренняя проверка restock не задерживает уже
причитающийся возврат. Сотрудник не отменяет законное право простым отказом одобрения.

Банковское зачисление зависит от провайдера, но не отменяет законный срок магазина:
CCR reg.34 — без неоправданной задержки и в применимый 14-дневный срок;
CRA s.20 при применимом отказе от дефектного товара — 14 дней от согласия продавца
с правом на refund. Сохранять основание/дату начала срока, контролировать pending/failed
и эскалировать до нарушения. «Возврат выполнен» только по подтверждению провайдера,
отдельно от банковского отображения зачисления.
[CCR](https://www.legislation.gov.uk/uksi/2013/3134),
[CRA](https://www.legislation.gov.uk/ukpga/2015/15/section/20),
[GOV.UK](https://www.gov.uk/accepting-returns-and-giving-refunds).
Самовывоз с принятием договора онлайн может также быть дистанционным договором:
оплата на месте сама по себе не отменяет эти права.

### Безопасность и CMS

Клиентские и служебные аккаунты/сессии разделены.
Проверка прав сервером для каждого действия, в том числе Payload Local API:
он по умолчанию может обходить access control; пользовательские вызовы с
overrideAccess:false и user, привилегированные — только внутри доменных действий.
[Local API](https://payloadcms.com/docs/local-api/overview).

### DD-03 — безопасные ссылки и доступ (Q-09)

Defaults оркестратора: CSPRNG 32 байта, opaque base64url token, SHA-256 хеш в БД,
TTL 15 минут от выпуска; purpose и email/конкретный Order связаны сервером.
Не удалять точки/plus в email. Истёкшая ссылка не отменяет заказ/резерв.
Подтверждение, потребление токена и привязка заказа атомарны, уникальность аккаунта
по принятой нормализации email обеспечивается БД. Не переносить другие неподтверждённые
заказы одного email, не перезаписывать профиль гостевыми данными.

GET только открывает подтверждение. Токен предпочтительно в URL fragment, клиент
удаляет его из адреса и передаёт в явном POST с CSRF/origin проверкой; кнопка
предотвращает расходование обычным mail scanner. При открытой чужой клиентской
сессии требуется явная смена аккаунта, без тихой привязки/подмены (login CSRF).
Обмен создаёт новую клиентскую сессию Secure/HttpOnly/SameSite=Lax, idle TTL 24h,
absolute TTL 7 дней, отзыв при logout. Ссылка на вход в историю — тот же механизм,
с отдельным purpose от claim Order; Staff Account через него недоступен.

Resend: cooldown 60 секунд, ≤ 5/час на email+purpose и ≤ 20/час на IP; общая БД.
Чужой неподтверждённый resend не отзывает действующую ссылку: ограниченные sibling
challenge допустимы, успешный обмен отзывает их только для того же purpose/Order.
Ответы/время нейтральны для нового и существующего email. Origin берётся из доверенной
конфигурации, не Host; redirect только разрешённый. Cache-Control:no-store,
Referrer-Policy:no-referrer, без аналитики/сторонних ресурсов/клик-трекинга на странице.
Токены, URL и email bodies не пишутся в app/access/error logs; open/click tracking
Postmark выключен. Числа — design defaults, не бизнес-требования.
Основа для токенов/нейтральных ответов —
[OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).

### Фоновые задачи

Outbox в одной транзакции с изменением заказа; процесс того же приложения получает
задачи блокировками БД, освобождает истёкшие резервы, отправляет письма и повторяет запросы.
Таймер только в памяти web неприемлем при росте/перезапуске.
Email не гарантирует exactly-once при потере ответа после принятия письма:
ключ события, возможности idempotency, обработка неопределённого результата.
Email-провайдер Postmark. Токен создаётся перед отправкой, чтобы очередь не доставляла
истёкшую ссылку; raw token не хранится в outbox. Неопределённая доставка сохраняет
challenge, ограниченный повтор создаёт новый токен без обещания exactly-once.

### DD-04 — managed hosting и восстановление (Q-06)

Предложение: DigitalOcean App Platform (web 2 GiB, worker 1 GiB), managed PostgreSQL
Standard 2 GiB и Spaces/CDN. Web/worker/БД предпочитают London; для объекта ближайший
доступный EU-регион, если UK недоступен. Ресурсы/договоры не созданы.
Смета, оговорки тарифов и альтернативы — [PROVIDERS](../../../docs/ai/PROVIDERS.md).
Плановый расход £90–125/месяц включает резерв на небольшое staging, независимые
backups и мониторинг внутри бюджета £75–150. Это оценка, не счёт/фиксированный курс.
Превышение £150 требует отдельного обоснования нагрузки/надёжности.

Production targets: RPO ≤ 5 минут для заказов, оплаты, возвратов, остатков, резервов
и outbox; RTO ≤ 4 часа для восстановления согласованной работы магазина.
PITR + WAL managed PostgreSQL — основа, ежедневного pg_dump недостаточно.
Single-node Standard восстанавливается при потере узла, не даёт мгновенный HA;
это ограничение минимального deployment. Цели не подтверждены до упражнения;
невыполнение требует изменить deployment, не принять 24h как финальную норму.
24h допустим только для локальной разработки/непроизводственного прототипа.

PITR хранит 7 дней; отдельные ежедневный зашифрованный dump и финансовый архив в
другом provider/account защищают от удаления кластера/компрометации. Dump имеет до
24h давности и не доказывает RPO 5 минут при потере всего provider. Это остаточный
риск: если те же цели должны покрывать такой сценарий, до запуска нужна независимая
непрерывная копия/реплика и отдельная смета. Scope и риск фиксируются в release evidence.
Финансовые документы/credit notes сохраняются до подтверждения двух копий; публичные
медиа восстанавливаемы из исходников/версий (цель ≤ 24h), не из локального диска web.

Runbook: остановить checkout/админ-продажи и side effects; новые Stripe events
сохранить безопасно для replay либо обеспечить последующую сверку, если БД недоступна;
восстановить новый кластер, проверить денежные итоги/резервы и физические продажи;
сверить платежи/refunds со Stripe за окно потери и неопределённые внешние операции;
отозвать восстановленные сессии/email tokens; переключить приложение, затем outbox.
Не повторять выполненный refund, письмо или restock из-за отсутствия факта в backup.
Физические продажи при outage фиксируются сотрудником во внешнем журнале и сверяются
до открытия; Stripe не восстановит их за магазин. Время сверки включается в RTO.
Упражнение до выпуска, затем ежеквартально и после изменений миграций/backup.
Контроль свежести восстановления/WAL, backup errors, очереди/worker, pending refunds,
места и оповещения ответственному. Нет обещания измеренной надёжности по одной цене.

### DD-05 — retention (Q-06)

Техническая policy оркестратора; 6-летний срок не распространяется на все данные.

| Данные | Default и очистка |
|---|---|
| VAT/финансовые записи, snapshots, invoice/credit notes, платежи/refunds, финансовый audit | 6 лет после конца соответствующего VAT accounting period; минимальные реквизиты, без полного профиля |
| Активный Customer Account | Пока используется; после 24 месяцев без активности предложить удаление/анонимизацию профиля с уведомлением за 30 дней; финансовые документы отдельно |
| Неподтверждённый аккаунт без заказов | 30 дней; при заказе сохраняется необходимая связь, доступа до проверки нет |
| Операционные app/error logs без тел/токенов | 30 дней |
| Security/access audit, кроме финансового | 90 дней, ограниченный доступ, минимизация IP где точное значение не нужно |
| Postmark email bodies/activity | Default провайдера 45 дней без open/click tracking; app хранит только metadata/результат 90 дней; юридически значимое подтверждение условий — в финансовом архиве |
| Email tokens | TTL 15 минут; хеш/привязка удаляются в течение 24h после expiry/use; raw token в логах отсутствует |
| Клиентские сессии | idle 24h/absolute 7 дней; удаление записи в течение 24h после expiry/revoke |
| Обработанные Stripe webhook payload | Минимизированный payload 30 дней; ledger event/payment/refund IDs и результаты для финансовой идемпотентности 6 лет; необработанные/спорные events не удалять автоматически |
| PITR/операционные backups | 7 дней у provider; независимые ежедневные dumps 30 дней, шифрование/отдельные права; финансовый архив отдельно 6 лет |

Удаление профиля не стирает законные финансовые записи. Restore снова применяет
журнал удалений/retention, не возвращая удалённые профили в production.
Спор/инцидент создаёт документированный hold на нужные записи с пересмотром.
Законный VAT минимум — [HMRC](https://www.gov.uk/charge-reclaim-record-vat/keeping-vat-records);
операционные сроки выбраны по принципу
[ICO storage limitation](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/data-protection-principles/a-guide-to-the-data-protection-principles/storage-limitation/).

### Проверка

Настоящая PostgreSQL: concurrent reserve/физическая продажа, expire/late payment,
webhook replay, cancel/payment race, самовывоз/expire/выдача и повторный restock.
VAT: смешанная корзина, 0%, HALF_UP, количества/последовательные partial refunds,
детерминированные остаточные пенсы доставки, неизменность снимков и смена tax point.
Email: expiry/use/resend, два одновременных claim, существующий email, чужая сессия,
GET scanner, token leakage. Восстановление и сверка side effects — DD-04.
Playwright: checkout/аккаунты/самовывоз/роли и API-доступ.
WCAG автоматикой и вручную; WebKit не заменяет реальный Safari/iOS.
Lighthouse лабораторно; CWV p75 по реальным данным. Отсутствие полевых данных не pass.
Performance score Lighthouse отдельно не утверждён.
Серверный HTML, canonical/sitemap/robots, достоверные Product/Offer/ProductGroup
где применимо; без фиктивных отзывов. llms.txt не обещает выдачу AI.

## Risks / Trade-offs

- Не зарегистрированная вовремя физическая продажа → сайт не знает о ней; нужен
  операционный порядок сотрудников, POS исключён.
- Просроченная готовность сохраняет резерв → календарь и эскалация сотруднику, не штраф клиента.
- Разный VAT/округление → DD-01 и реальные классификации/tax point до выпуска.
- Refund pending/failed → показывать факт состояния, не успешный запрос как возврат.
- Single-node/общий provider → DD-04, измеренная recovery, независимые копии; не обещать HA.
- Email/hosting персональные данные → DPA/регион/retention до production.
- Прямой edit CMS → запрет обхода финансовых/складских доменных действий.

## Migration Plan

Наследуемой системы нет. Выпуск требует backup/restore проверки и обратной совместимости
миграций при нескольких web-репликах, сохранения webhook обработки при rollback.
Конкретные команды появятся после приложения; сейчас их исполнение не проверено.
